# Rehearsal frontend

React workspace for the integrated disruption → review → recovery → rehearsal
→ approval/export flow. The production build calls the same-origin FastAPI
backend. AMD interpretation runs on the server; the browser holds no AMD key.

See the [project guide](../README.md), [architecture](../docs/ARCHITECTURE.md)
and [native setup](../docs/DEVELOPMENT.md). The earlier factory-only and
approval-only development servers are isolated helpers, not the full application.

## Run

Use Node **22.12 or newer** and npm. From the repository root:

```bash
npm --prefix frontend ci
VITE_USE_MOCKS=0 npm --prefix frontend run dev -- --port 5173
```

Start `app.main:app` on port 8000 using the [development instructions](../docs/DEVELOPMENT.md).
Open http://localhost:5173. The Vite proxy forwards `/api` to `127.0.0.1:8000`.
For PowerShell, set `$env:VITE_USE_MOCKS="0"` before the npm command.

| Source | Behavior |
| --- | --- |
| Live API + configured AMD | Real extraction, validation, solving, checking, replay and approval against the backend |
| Live API + explicit rule fallback | Real local workflow, with interpretation visibly labeled as fallback rather than AMD |
| Recorded samples | Deep-copied saved responses for previews; no model, solver or replay call and no new approval |

Plain `npm run dev` defaults to Recorded samples; `VITE_USE_MOCKS=0` selects live
mode at startup. The source selector remains available. Production builds
normally default to Live API; the Docker build explicitly sets that mode.
The frontend never silently replaces a failed live request with samples.

`VITE_API_BASE_URL` can point at a different API origin if the backend permits
CORS from the frontend origin. Leave it empty for the development proxy or
same-origin production deployment. All `VITE_*` settings are public browser
configuration: never put credentials in them.

## Build and checks

```bash
npm --prefix frontend test
npm --prefix frontend run build
npm --prefix frontend run preview -- --port 4173
```

`frontend/dist` is static output. The preview server has no backend API proxy;
use it to preview Recorded samples, or configure `VITE_API_BASE_URL` before
building. To run the complete production app, serve the build through FastAPI
or [Docker](../docs/DOCKER.md). Fonts are local assets with their SIL OFL notices
in `public/fonts/`.

The Node test runner covers transport failures/cancellation, response boundaries,
review gates, checker state, timeline and approval helpers without downloading a
browser. Historical [factory](../docs/FACTORY_VIEW_QA.md),
[checker](../docs/CHECKER_QA.md), [workflow](../docs/WORKFLOW_QA.md),
[robustness](../docs/ROBUSTNESS_QA.md) and [approval](../docs/APPROVAL_QA.md)
reports describe their feature-stage checks. The latest
[public AWS evidence](../docs/AWS_DEPLOYMENT.md) verifies the integrated app
with real AMD access.

## Integration contracts

`src/components/CheckerResult.jsx` accepts `result: {valid, violations}` plus
optional `title` and `description`. It renders every violation as text and
fails closed for missing, malformed or inconsistent results. Alternative
cards, approval and the run inspector use it with their own backend results. The existing solve/approve response shapes are unchanged.

`shared/checker-reports.json` is generated by the real Python checker against
the existing synthetic fixture and sample constraints. The comparison under
Sample recovery shows why the committed schedule fails after the outage.
Run the freshness check from the repository root when those inputs change:

```bash
PYTHONPATH=backend python3 -m app.checker_report --check
```

See [backend checker instructions](../backend/README-checker.md) for direct
calls, report regeneration and rule coverage. Matching source hashes and
recomputed reports are checked in Python, rather than trusting the saved
`valid` flag as evidence of a new calculation. No checker HTTP endpoint or
additional AMD request is needed.

`src/lib/api.js` exports `api(path, body?, options?)` and
`createApi({useMocks, baseUrl, fetchImpl})`. Body omitted means GET; a supplied
body means a JSON POST. `options.signal` supports cancellation. Successful mock
responses are deep copies. Errors carry `code`, `status`, `retryable`, and the
backend's canonical message. Existing factory/extract/solve/replay/approve mock
responses are saved in `shared/mocks/` and follow `plan/03_API_CONTRACT.md`.
The mock transport refuses `/approve`: recorded artifacts cannot confirm a new
approval. Mock `/health` is intentionally unsupported rather than inventing
AMD configuration. `App.jsx` owns workflow state and uses the shared transport.

`src/components/Timeline.jsx` is independent of the examples:

| Prop          | Shape / meaning                                                                 |
| ------------- | ------------------------------------------------------------------------------- |
| `machines`    | Fixture machine objects, in row order; empty machine rows are supported         |
| `jobs`        | Fixture jobs; array order determines stable job colors                          |
| `schedule`    | Array of `{job, op, machine, start, end, change?, segments?}`                   |
| `now`         | `HH:MM`, factory local time                                                     |
| `shift`       | Fixture shift; `start`, `end`, optional `overtime_until`                        |
| `outages`     | `{machine, from, until}[]`; defaults to empty                                   |
| `dueMarkers`  | `{job, time}[]`; coincident/nearby markers use separate lanes                   |
| `highlight`   | `{job, op?}` or array of `"job:op"` keys; defaults to empty                     |
| `selectedKey` | Selected operation key such as `"J7:2"`                                         |
| `onInspect`   | Callback receiving an operation on hover, click, keyboard focus, Enter or Space |
| `label`       | Accessible schedule name                                                        |

The viewport derives its bounds from shift, schedule, outages and due markers,
so overtime is not clipped. The selected-operation detail lives outside the
SVG. The component itself does not know solver, checker, replay, concession, or
AMD semantics. Frozen styling describes started work; the approval service owns
approval decisions.

An interrupted operation may provide `segments: [{start, end, kind}]`, where
`kind` is `interrupted` or `restart`. The component paints only those processing
segments and leaves the repair wait as a gap. It remains one logical operation
for selection and machine counts; its outer start/end includes elapsed waiting
time. Accessible descriptions list the segments. Old schedules without this
optional field render as before.

`src/lib/timeline.js` supplies strict clock parsing, schedule-derived delivery
outcomes, stable operation keys, and optional sample annotations.
`shared/fixture.json` and all six `shared/mocks/*.json` are byte-for-byte copies
of the checked plan. Do not regenerate them as a side effect of running the UI.

## Checks and manual QA

`npm test` checks fixture integrity, delivery outcomes from all three schedules,
time bounds, coincident due markers, annotation preservation, mock isolation,
live GET/POST requests, canonical errors, malformed responses, offline behavior,
and cancellation. These use the Node test runner and need no browser download.

For browser QA, verify the three view controls, order Locate/Clear buttons,
operation hover and keyboard focus, source switching, retry after a stopped
backend, and timeline horizontal scrolling at narrow sizes. Spot-check J1·2
09:20–10:05 on Mill M2; J6·2 10:10–11:35 on Mill M1; J7·3 13:25–13:55 on Lathe
L3 in the committed view. The saved recovery has J2 190 minutes late; the saved
failure has J4 61 minutes late. Hatching in the failure shows the **nominal**
outage: the replay response does not supply sampled repair-end metadata.
